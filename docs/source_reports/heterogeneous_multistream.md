## 4. 四条结论

### 4.1 提高前向质量会直接吃掉总吞吐

以 CONFIG-A 为基准（全 320×192，25.72 FPS）：

| 配置 | 聚合 FPS | 相对 A | FRONT 画布 |
| --- | ---: | ---: | --- |
| CONFIG-A | 25.72 | — | 320×192 |
| CONFIG-B | 23.86 | −7.2% | 512×288 |
| CONFIG-C | 22.91 | −10.9% | 512×288 + 侧路 416×256 |
| CONFIG-D | 22.42 | −12.8% | 640×352 |

把 FRONT 从 320×192 提到 512×288 的代价是总吞吐的 7.2%；再给侧路加分辨率到 416×256 是 10.9%；FRONT 到 640×352 是 12.8%。

代价的来源可以直接算：FRONT 每帧 NPU 时间从 20.5 ms 升到 36.5 ms（+16 ms），10 FPS 下多占 160 ms/s。

### 4.2 单流最高帧率受"聚合吞吐 ÷ 流数"约束

四路共用一个 NPU，在聚合 ~25.7 FPS 时每路的平均服务间隔是 `流数 ÷ 聚合 = 4/25.7 = 156 ms`。
如果某路的目标周期短于这个间隔（FRONT @10 FPS = 100 ms），它的队列就会溢出。

所以**均分调度下每路最多只能到 ~6.4 FPS**。想让 FRONT 到 10 FPS，必须用优先级把 FRONT 的时隙份额提到 40% 以上，
代价是侧路按比例下降——CONFIG-B（rate）的实测正是 FRONT 8.97 / 侧路 4.96。

### 4.3 调度器选型的影响远大于画布调整（本轮最大发现）

CONFIG-B 与 CONFIG-B-WRR 的**流定义、画布、目标帧率完全相同**，只有调度器不同：

| 指标 | CONFIG-B（rate，最迟优先） | CONFIG-B-WRR（weighted 5:2:2:1） |
| --- | ---: | ---: |
| 聚合 FPS | 23.86 | **27.54**（+15.4%） |
| FRONT 达成率 | 0.897 | **1.000** |
| LEFT/RIGHT 达成率 | 0.827 | **1.000** |
| BACK 达成率 | 0.827 | 0.921 |
| 丢帧率 | 11.2% / 18.1% / 18.1% / 18.1% | **1.1% / 1.1% / 1.2% / 8.9%** |
| e2e p95（FRONT / 侧路） | 370 / 531–546 ms | **141 / 223–225 ms** |
| 队列均值 | 3（满） | 2 |

`RateDeadlineScheduler` 的"最迟优先"在饱和时会制造突发：当一个 52 ms 的 FRONT 帧占用 NPU 时，
其他三路的 due 时间同时过期，接下来会被连续服务，期间新帧继续按目标速率到达，队列因此堆到上限并开始丢帧。
`WeightedRoundRobinScheduler` 的信用机制天然把这些帧摊平，队列不堆、尾延迟降 2–3 倍。

**结论：加权轮询是这个场景的正确选择，"最迟优先"不是。**

### 4.4 权重必须按目标帧率比来定，不能凭直觉排优先级

CONFIG-B-WRR 用 5:2:2:1 时，BACK 只分到约 10% 时隙（≈2.75 FPS），低于它 6 FPS 的目标，
因此 BACK 是唯一还在丢帧的一路（8.9%）、也是尾延迟最差的一路（p95 498 ms）。
权重改为与目标帧率成比例的 10:6:6:6（CONFIG-B-WRR-FAIR）即针对此修正。

权重改为 10:6:6:6 后，唯一的欠配路消失：

| 指标 | 5:2:2:1 | **10:6:6:6** |
| --- | ---: | ---: |
| 聚合 FPS | 27.54（0.983） | **27.91（0.997）** |
| FRONT | 10.00（1.000） | 9.96（0.996） |
| LEFT / RIGHT | 6.00 / 6.00（1.00） | 5.99 / 5.99（0.998） |
| BACK | 5.53（0.921） | **5.98（0.997）** |
| BACK 丢帧 | 8.9% | **1.4%** |
| BACK e2e p95 | 498 ms | **457 ms** |
| 队列均值（BACK） | 1.74 | **1.51** |

**规则：加权轮询的权重应取目标帧率之比。** 把权重理解成"优先级阶梯"（5:2:2:1）会让最低权重的
那一路拿不到它需要的时隙，在多数流都没打满时会被别的流"吃掉"余量、而在边缘时刻开始丢帧。


### 4.5 请求超过服务上限只会换来丢帧

PROFILE-2 把总量提到 29（FRONT 12），达成率掉到 0.843，FRONT 实际 9.95（目标 12），丢帧 16.8–17.9%。
FRONT 的 12 FPS 目标在四路共享下不可持续——按 §4.2 的约束，FRONT 要到 12 FPS 就需要 48% 的时隙，
留给三路各只有 4.5 FPS。**把请求设定在实际服务能力之下，队列才会保持短、e2e 才会低。**


### 4.6 队列深度是延迟旋钮（深度 1 vs 3）

同样配置（CONFIG-B-WRR-FAIR）只改队列深度：

| 指标 | depth 3 | depth 1 |
| --- | ---: | ---: |
| 聚合 FPS | 27.91（0.997） | 27.41（0.979） |
| FRONT / 侧路 丢帧 | 1.6% / 1.4% | 2.3% / 3.4% |
| FRONT e2e p95 | 314 ms | **146 ms** |
| FRONT 平均等待 | 117.6 ms | **31.1 ms** |
| 侧路 e2e p95 | 446–457 ms | 167–181 ms |

队列深度直接决定"被服务的帧有多旧"：drop-oldest 的队列里保留的是最新的 N 帧，服务的是其中最旧的一帧，
所以等待 ≈ 深度 × 服务间隔（4/27.9 = 143 ms）。深度 3 → 最多约 430 ms，深度 1 → 约 143 ms，
与实测吻合。

### 4.7 关于 e2e 延迟的口径

本文件所有 `e2e` 都是 `post_done_ts - arrival_ts`，即"帧从解码完成到后处理结束"。
它**包含**排队等待，**不含**解码耗时（解码发生在 arrival_ts 之前）。
引用时请注明深度，否则同一个配置可以有 146 ms 和 314 ms 两个"正确"的 p95。

## 5. 20 分钟长测与 300s/600s 差异归因（2026-09-18 追加）

### 5.1 先回答"为什么 300s 是 27.91、600s 只有 23.66"

**根因：测量协议差异，不是性能退化。** 查配置文件可直接证实：

| 运行 | 时长 | 调度器 | 队列深度 | 聚合 FPS |
| --- | ---: | --- | ---: | ---: |
| CONFIG-B-WRR-FAIR | 300 s | **weighted 10:6:6:6** | 3 | 27.91 |
| CONFIG-B-10MIN | 600 s | **rate（优先级 3:2:2:1）** | 3 | 23.66 |
| CONFIG-B（rate 的 300s 基线） | 300 s | rate | 3 | 23.86 |

600s 那次用的调度器与 27.91 那次**根本不同**。同协议对比：rate 调度 600s（23.66）对 300s（23.86）
只差 -0.8%，在噪声范围内；WRR-FAIR-D1 300s（27.41）对 1200s（27.30）只差 -0.4%。
**长时运行本身没有衰减。**

### 5.2 20 分钟遥测长测（WRR-FAIR-D1，修复协议后的正式长测）

配置：FRONT 512×288@10 + 三路 320×192@6，weighted 10:6:6:6，深度 1，drop-oldest，1200 s。

| 丢帧 | 1.8% | 1.5% | 3.4% | 5.3% | 3.0% |
| NPU mean | 35.7 ms | 19.9 | 19.3 | 19.0 | — |

（+1.4%，无衰减）。无路由错误、无崩溃、无重启。

### 5.3 归因判定

- THERMAL THROTTLING：**排除**（最高 38.9 °C，NPU 恒 600 MHz）。
- DECODE BOTTLENECK：**排除**（解码在各流独立线程，20 min 内吞吐无下降）。
- SCHEDULER / QUEUE ISSUE：**排除**（20 min 无错误、无饥饿漂移）。
- MEASUREMENT PROTOCOL DIFFERENCE：**确认，这就是根因**（600s 测试用了 rate 调度器）。

### 5.4 正式配置以长测为准

正式口径：**WRR-FAIR-D1 配置连续运行 1200 s = 27.30/28 FPS（97.5%），FRONT 9.85 FPS**。
较 300s 深度 1 运行（27.41）低 0.4%，属正常波动。
